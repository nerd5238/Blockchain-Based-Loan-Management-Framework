Security Model

How this system prevents data tampering

Zero-Trust Audit Layer

Every loan record is fingerprinted with SHA-256 and that fingerprint is burned into an immutable blockchain — making silent data tampering mathematically impossible to hide.

How tampering is prevented
SHA-256 fingerprinting
Every field of every loan record — loanId, userId, amount, interest, duration, status, timestamp — is serialised in a fixed order and hashed. Changing even a single character (e.g. amount from 50000 to 50001) produces a completely different hash.
sha256(loanId+userId+amount+interest+duration+status+timestamp)
Blockchain immutability
The smart contract uses a require(!records[loanId].exists) guard — a hash can only be written once. Once stored on Ganache, it can never be overwritten or deleted. No admin, no root user, nobody can change it.
require(!records[loanId].exists, "immutable");
Tamper detection at verify time
When you call Verify, the backend re-hashes the current DB record and compares it against the blockchain. If a database admin edited the record directly (bypassing the API), the hashes won't match — exposing the tampering instantly.
recomputedHash !== blockchainHash → TAMPERED
Append-only audit trail
Every update creates a new versioned blockchain entry (UPDATE-LOAN-001-1, UPDATE-LOAN-001-2...). The full history is preserved — you can audit every state change a loan ever had, and each checkpoint is verified independently.
storeRecord("UPDATE-LOAN-001-1", newHash)
Backend-only blockchain access
No browser ever talks to Ganache directly. All Web3 calls go through the Node.js backend, which controls the signing account. Users interact only with REST APIs — the blockchain layer is completely opaque to the outside world.
User → Express API → Web3.js → Ganache
Attack scenario: direct DB edit
Suppose an attacker gains MongoDB access and changes a loan amount from ₹50,000 to ₹5,000. The DB record looks fine. But the next Verify call re-hashes the edited record — it gets a different hash — and the blockchain still holds the original. Result: instant TAMPERED alert.
DB edit → hash mismatch → audit alert
What this system does NOT protect against
✕ API-level manipulation — if someone calls the API with fraudulent data before it's saved, that fraud gets hashed and stored. Blockchain only protects what's already recorded.
✕ Ganache is local — for production, use a private permissioned chain (Hyperledger Besu, Quorum) so the blockchain itself isn't on the same machine as the attacker.
✕ No authentication — this demo has no login system. In production, add JWT/session auth to the API endpoints.
